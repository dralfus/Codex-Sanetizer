# Контекст AI-разработки проекта

Версия workflow-комплекта: `1.1`

## Текущая стадия

Требования, спецификация и tickets уже подготовлены. Текущая работа начинается
с выбора одного ticket и не перезапускает весь этап проектирования без
конкретной необходимости.

Перед началом работы Controller должен получить точные пути к:

- ticket;
- связанной спецификации;
- проектным инструкциям и командам проверки;
- fixed point для проверки diff.

## Используемый workflow

```text
requirements -> specification -> tickets -> implementation -> independent
review -> executable verification -> DONE или BLOCKED
```

Matt Pocock skills используются для уточнения требований, спецификации и
декомпозиции. Superpowers и multi-agent orchestration используются для
разделения реализации и независимой проверки.

## Наблюдаемая проблема

Implementation-агенты могут объявлять ticket завершённым, хотя ручная проверка
или review обнаруживают пропущенные требования, заглушки и преждевременно
закрытые checkbox.

Рабочая гипотеза: основная причина — смешение реализации и полномочий приёмки,
а не только качество конкретной модели.

Второй наблюдаемый failure mode: независимая приёмка может превратиться в
дорогой архитектурный repair-loop, если один finding повторяется, Reviewer
создаёт собственных subagents, полный suite запускается до статического PASS или
новые требования принимаются без adjudication. Такой цикл останавливается как
`BLOCKED_FOR_DESIGN`, а не продолжается до исчерпания пяти раундов.

## Целевая модель полномочий

- Implementer реализует ticket и сообщает `IMPLEMENTED`.
- Reviewer независимо проверяет соответствие спецификации и качество кода.
- Verifier собирает исполняемое evidence по acceptance criteria.
- Controller сопоставляет вердикты с evidence и присваивает `DONE` или
  `BLOCKED`.

Полный операционный протокол находится в `task-lifecycle.md`.
