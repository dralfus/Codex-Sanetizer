# Как выполнить одну задачу разработки

Версия комплекта: `1.1`

Эта инструкция предназначена для человека. Используйте её, когда требования,
спецификация и tickets уже подготовлены и нужно реализовать один ticket.

## Один раз для проекта

Скопируйте в корень проекта содержимое каталога `project-workflow-kit`, сохранив
структуру:

```text
<project>/
├── AGENTS.md
├── task_dev_instuction.md
└── docs/
    └── ai-workflow/
        ├── context.md
        └── task-lifecycle.md
```

Если в проекте уже есть `AGENTS.md`, сохраните его проектные правила и добавьте
в него workflow-раздел из комплекта. Не заменяйте существующий файл вслепую.

В `docs/ai-workflow/context.md` актуализируйте пути к спецификации и tickets,
если они отличаются от принятых в проекте.

## Перед началом ticket

1. Выберите один незакрытый ticket.
2. Убедитесь, что у него есть проверяемые acceptance criteria.
3. Откройте в Codex Desktop корневую папку проекта.
4. Создайте новую Codex task для Controller либо продолжите существующую
   Controller task, если её контекст остаётся управляемым.

## Prompt для Controller

Скопируйте весь блок ниже и замените значения в угловых скобках:

```text
Ты — Controller одной задачи разработки.

Ticket: <TICKET_FILE_OR_ID>
Спецификация: <SPEC_PATHS>

До начала работы полностью прочитай:
- AGENTS.md;
- docs/ai-workflow/context.md;
- docs/ai-workflow/task-lifecycle.md;
- указанный ticket и связанные документы спецификации.

Работай в текущей открытой рабочей папке. До запуска Implementer самостоятельно
определи и сообщи:
- абсолютный путь рабочей папки;
- является ли она Git-репозиторием;
- текущую ветку и commit;
- fixed point, относительно которого будет проверяться diff.

Если Git не используется, выбери другой воспроизводимый baseline и объясни его.

Файл docs/ai-workflow/task-lifecycle.md является обязательным протоколом.
Если обязательный файл недоступен или инструкции противоречат друг другу,
верни NEEDS_CLARIFICATION и не начинай реализацию.

Перед запуском каждого агента, включая повторный запуск после исправления,
выведи:
- номер раунда;
- роль агента;
- сложность задачи: простая, обычная, сложная или критичная;
- уровень риска: низкий, средний, высокий или критичный;
- выбранную модель и reasoning effort;
- краткую причину выбора;
- изменение модели/effort относительно предыдущего раунда либо «эскалации нет».

При усилении явно покажи переход, например:
`Terra medium -> Terra high`, и объясни его причиной предыдущей неудачи или
наблюдаемого риска.

До реализации также сообщи:
- ожидаемые компоненты и верхнюю границу числа изменяемых файлов;
- evidence для каждого acceptance criterion;
- условия ранней остановки цикла;
- требуется ли архитектурное решение до написания production-кода.

Не реализуй ticket самостоятельно. Только Controller может создавать subagents.
Запрети Implementer, Reviewer и Verifier создавать дочерних агентов. Выполни
полный цикл из task-lifecycle.md. Только Controller может присвоить DONE после
независимого ACCEPTED.

Сначала запускай Reviewer. Verifier и полный test suite разрешены только после
SPEC: PASS и CODE_QUALITY: PASS. Повтор одной корневой причины во втором
fix-раунде переводит ticket в BLOCKED_FOR_DESIGN. После двух неуспешных
fix-раундов запроси у пользователя разрешение на продолжение.

В финале сообщи статус ticket, acceptance evidence, команды и результаты,
написанные или изменённые тесты, полную историю моделей и effort по раундам,
findings, число fix-раундов и пути к сохранённым артефактам.
```

## Что происходит дальше

Controller должен:

1. самостоятельно определить рабочую папку и fixed point;
2. проверить ticket, оценить сложность, риск, ожидаемый scope и условия ранней
   остановки и сообщить выбранную модель;
3. создать Implementer;
4. дождаться `IMPLEMENTED`;
5. создать одного независимого Reviewer без дочерних агентов;
6. только после `SPEC: PASS` и `CODE_QUALITY: PASS` создать Verifier;
7. при подтверждённом `REJECTED` выполнить adjudication и scoped fix;
8. при повторе корневой причины или design gap остановиться как
   `BLOCKED_FOR_DESIGN`;
9. завершить ticket как `DONE` только после подтверждённого `ACCEPTED`;
10. после пяти разрешённых, но неуспешных fix-раундов завершить цикл как
    `BLOCKED`.

Не принимайте ticket самостоятельно по сообщению Implementer. Дождитесь
финального отчёта Controller с evidence.

## После завершения ticket

Если статус `DONE`:

1. Проверьте, что evidence сохранён в файлах проекта или каноническом
   workflow-хранилище.
2. Архивируйте задачи Implementer и Reviewer/Verifier.
3. Выберите следующий ticket и повторите эту инструкцию.

Если статус `BLOCKED_FOR_DESIGN` или `BLOCKED`:

1. Не помечайте ticket выполненным.
2. Проверьте, что Controller записал тип задачи, причину блокировки, выполненные
   попытки, модели/effort и следующий диагностический шаг.
3. Разбирайте закономерности блокировок отдельно от цикла реализации.

## Возобновление после паузы

Не продолжайте старый repair-loop автоматически. Новый Controller сначала
получает checkpoint, проверяет partial diff и решает, сработало ли условие
`BLOCKED_FOR_DESIGN`. Если архитектурное решение отсутствует, новый Implementer
не запускается. Если решение уже зафиксировано, свежему Implementer передаются
только baseline, текущий diff, targeted RED/GREEN состояние и нерешённые
findings.

## Когда менять Controller

Один Controller можно использовать для нескольких последовательных tickets.
Создайте нового Controller, если:

- контекст стал слишком большим;
- Controller смешивает состояния разных tickets;
- началась новая крупная функция или новый этап проекта;
- Controller участвовал в реализации и больше не является независимым;
- инструкции или версия workflow существенно изменились.

Новому Controller передавайте только актуальные документы, следующий ticket и
ссылки на сохранённое evidence.
